# 前端 Demo v1 规划：从单机预览到双人共用

> 最后更新：2026-10-28
> 状态（2026-10-28）：Demo 1.5 已完成；账号、空间、邀请、库存、待办、生活记录与自动部署均已接通，下一阶段进入真机弱网与稳定性验证。
> 上位文档：`docs/04-mvp-implementation-plan.md`（范围基线）、`docs/05-frontend-demo.md`（Demo 1.2 现状与视觉基线）。
> 本文解决一个问题：**在前端本地 MVP Demo 1.2 的基础上，怎么花最少的成本，做出一个 1–2 个人真正每天在用、且以后能扩展的版本。**

## 0. 需求理解（先对齐）

| 约束 | 含义 |
| --- | --- |
| 短期 1–2 人使用 | 不需要扛并发、不需要多租户运营后台、不需要监控体系 |
| 最小成本跑起来 | 增量费用接近 0；能用已有服务器 / 域名 / COS；运维动作尽量少 |
| 后期会慢慢推广 | 数据模型、分层、接口契约要能扩展；不能把业务流程写死在前端页面里 |
| 迭代要考虑扩展性和维护性 | 每个模块有固定骨架、契约单一来源、迁移可回滚、旧版本小程序不被破坏 |

**一句话结论**：最小成本 ≠ 最少组件，而是**最少的运维动作 + 不返工的分层**。已经有的 MySQL / Caddy / COS 直接用，比自己造轮子更省。

## 1. 阶段判断：本地 MVP 的真实短板

前端 MVP Demo 1.2 已经补齐登录注册和主要模块的本地操作深度，当前短板不再是页面或表单数量，而是**本机账号与单机数据无法形成真实的双人共同空间**。

| 维度 | 现状 | 问题 |
| --- | --- | --- |
| 页面广度 | 18 个页面，库存/宠物/菜单/记录/邀请/提醒都有 | 足够讨论产品方向 |
| 数据深度 | 全部存 `wx.getStorageSync`，单机 | 两个人用的是两份互不相干的数据，"共同空间"这个核心不成立 |
| 真实感 | 首页同时展示库存、宠物照护、菜单、记录 | 用户会以为宠物和记录也同步了，实际只在本机 |
| 工程 | 双模式请求层、账号/空间/邀请 Gateway、135 项自动测试与两套运行时验收脚本 | 登录与邀请已真实联调；库存仍是下一块需要切换的 Gateway |
| 设计系统 | 色板/圆角/阴影散落在各页面 WXSS | 加页面就会继续漂移，Logo/TabBar 无法统一 |

**所以 Demo v1 的目标不是"再加页面"，而是把已经可操作的本地 MVP 升级为"可双人共用的日常工具"，其余模块明确保留本机标识。**

## 2. 唯一验收标准

> **两个人、两台手机、同一个空间，看到同一份库存，互相修改能立刻看到；7 天日常使用不需要人教。**

只要这一条不成立，加多少页面都不算进入下一阶段。反过来，这条成立之后，宠物、菜单、记录才有资格逐个"上云"。

## 4. 设计思路（四条原则）

### 原则一：单一主链路优先
家 → 库存 → 到期提醒 → 邀请。所有工程投入先服务这条链路，其他模块只做"不被误解"的处理，不做功能增强。

### 原则二：页面不感知数据来源
页面只依赖 `Gateway` 接口。`demoMode` 用本地 Mock，`liveMode` 用 HTTP，由工厂切换。这样：没网也能演示，用真数据时页面代码不变，也天然形成"可回退"能力（后端挂了可临时切 demo 保命）。

### 原则三：契约先行，但只定用得上的那部分
`openapi.yaml` 是唯一契约。但不在第一天写完所有接口——每上一个里程碑，只冻结该里程碑用到的接口，其余留空。冻结后前端按契约写映射，不猜字段。

### 原则四：先收设计系统，再扩页面
页面数量已经够多了，继续加页面必须先有 token 和组件，否则圆角、颜色、间距会继续漂移。**Demo v1 期间不再新增业务页面**，只做既有页面的重构与状态补齐。

## 5. 前端架构

### 5.1 分层

```text
pages/            页面：只做加载编排、事件绑定、组装视图数据
components/       展示与局部交互
domain/           纯函数：规则、推导、格式化、DTO↔domain 映射（可单测，不碰 wx）
services/         数据访问：Gateway 接口 + Mock 实现 + HTTP 实现 + 工厂
stores/           跨页面稳定状态：session、activeSpaceId
config/           环境常量（baseUrl、demoMode）
types/            API DTO 类型
utils/            导航、TabBar 同步等平台适配
```

硬约束：**页面里不允许出现 `wx.request`**；四层中只有 `services/` 可以碰网络与存储。

### 5.2 Demo / Live 双模式

```ts
// services/gateway.ts
export const gateways = {
  inventory: config.demoMode ? mockInventoryGateway : httpInventoryGateway,
  journal:   config.demoMode ? demoJournalStore    : httpJournalGateway,
}
```

- `demoMode` 由 `config/env.ts` 的编译期常量决定，生产构建恒为 `false`。
- Mock 实现与 fixtures **保留**：单元测试、离线演示、后端故障时的手动回退都靠它。
- 每个模块切换时，页面不改，只改工厂里那一行 —— 这是"逐个模块上云"的基础。

### 5.3 页面状态规范（每个数据页面必须四态齐全）

| 状态 | 表现 |
| --- | --- |
| loading | 骨架屏（列表页）或按钮 loading（表单页），不整页白屏 |
| empty | 有空态插画/文案 + 下一步动作（如"添加第一件物品"） |
| error | 错误文案 + 重试按钮；网络错误与业务错误文案区分 |
| success | 正常内容 |

### 5.4 弱网与一致性

- 列表：下拉刷新 + 触底加载更多（游标分页），失败保留已有内容并提示。
- 写操作：`Idempotency-Key` 复用同一次重试，避免重复入库。
- 并发编辑：`version` 乐观锁，冲突时详情页自动重载并提示"物品已被更新"，不静默覆盖。
- 401：单飞重登一次再重放，避免并发 `wx.login` 互相覆盖 token。

## 6. 信息架构与页面设计要点

| 页面 | Demo v1 变化 |
| --- | --- |
| `home` | 摘要改读服务端 `summary`；宠物卡片降权并标"本机预览"；菜单卡片保留为"即将同步"；去掉任何暗示已同步的文案 |
| `inventory` | 摘要 + 服务端筛选 + 游标分页；分段标题改为遍历有序列表时按 `expiryStatus` 变化插入；顶部加"共享空间"标识 |

| `item-detail` | 冲突后自动重载；状态操作与删除保持现有交互；显示"最后修改人"（多人协作时最有用的信息） |
| `space` | 空间名、成员列表（头像/昵称/角色）、邀请入口 |
| `invite` | 支持分享路径带码；校验失败区分"无效/已过期/已被使用" |
| `profile` | 显示当前身份与当前空间；Demo 工具保留但收进"开发者"分组 |
| `journal` / `journal-form` | Demo v1 保持本地，但标注"本机记录"；P1 上云 |
| `pets` 四页 | 全部标"本机预览"；首页不再展示其照护状态为"今日待办" |
| `menu` | 标"示例数据" |
| `reminder-settings` | 标"即将支持" |

**新增一个全局组件：`sync-badge`（数据来源标识）**

- `shared`：共享空间数据（云朵/对勾图标 + 无文字或"已同步"）
- `local`：本机数据（"本机"标签，灰蓝底）
- 规则：每个展示数据的卡片/列表头都必须能判断来源；不允许出现"看起来是共享但其实是本机"的内容。

这是本轮最重要的产品设计动作 —— 它用极低成本解决了"两个人用但数据不通"带来的信任问题。

## 8. 后端与基础设施最小集

### 8.1 技术选型（沿用 `docs/04`）

```text
Go 单二进制 + chi + MySQL（服务器已有实例，独立库） + systemd + Caddy/Nginx
迁移 goose；查询 sqlc；日志 slog；契约 OpenAPI
```

**关于 MySQL vs SQLite 的取舍**：1–2 用户下 SQLite 技术上完全够，备份就是拷文件。但服务器上已有稳定 MySQL，增量成本为 0，而 SQLite 会带来方言差异（与 `docs/06` 的 sqlc 设计冲突）、并发写锁、将来迁移成本三项负债。结论：**沿用 MySQL**；只有当现有 MySQL 版本过旧或占用风险大时才切换。

### 8.2 COS 的使用节奏

| 阶段 | 用途 | 是否必要 |
| --- | --- | --- |
| Demo v1 | 数据库每日备份（`backups/popcorn/mysql/`） | 必要 |
| Demo v1 | 不承载用户图片 | — |
| 推广期 | 物品照片、宠物照片（私有前缀 + 短期签名 URL） | 后续 |

前期不为图片预留任何前端入口，避免"功能半成品"。

### 8.3 发布策略（成本关键）

- **先用微信「体验版」跑**：加你和家人为体验成员即可，不需要审核、不需要备案完成，零成本启动。
- 合并到正式发布前再做：小程序备案、类目、隐私协议、API 合法域名配置。
- 这能把"跑起来"的时间从数周（审核+备案）压缩到数天。

### 9.2 每个里程碑的工作节奏

1. **一个里程碑一个分支**，合并前必须：`npm test` + `npm run typecheck` + 真机截图。
2. **切换粒度按模块，不按页面**：库存整体切完后，`pages/inventory`、`home`、`item-*` 一次性验证，避免长期处于半接状态。
3. **每个里程碑结束回写文档**：`docs/05` 记录实际操作路径与验收结果，架构变化回写 `docs/04` / `docs/06`。
4. **M3 结束做一次"陌生设备测试"**：让家人按真实路径自行加入，观察是否需要口头指导 —— 这是产品可用性的唯一硬指标。
5. 生活记录已完成；后续仍按**每 2 周一个模块**推进菜单与宠物云同步，每个模块都按 §5.1 的骨架新增。

## 10. 扩展性与维护性的具体落点

不是口号，落到可检查的约束：

| 关注点 | 具体约束 |
| --- | --- |
| 新增业务模块 | 固定五件套：表 + 迁移、repository、service/handler、OpenAPI 片段、前端 domain+gateway+page；缺一件不合入 |
| 数据隔离 | 所有业务表必须带 `space_id`；所有查询必须带 `space_id` 条件（code review 检查项） |
| 不做万能表 | 宠物/记录/菜单各自建表，不塞进通用 `records` 表 |
| 契约 | 字段 `camelCase`；日期 `YYYY-MM-DD`、时间戳 UTC RFC3339；错误结构统一；改字段先加后删 |
| 迁移 | goose 顺序编号；每个迁移可回滚；一次发布内不做破坏性变更 |
| 旧版本兼容 | 小程序存在"用户不更新"的情况：新增字段必须可选；删除字段分两阶段；接口不设置 URL 版本前缀；破坏性调整通过新路径处理 |
| 前端边界 | 页面不碰网络/存储；纯规则放 `domain/` 以便单测；组件不发请求 |
| 测试 | `domain/*` 与 gateway 映射必测；到期边界用例 Go 与 TS 各一份且值一致；不追求覆盖率数字 |
| 观测 | `requestId` 贯穿请求与日志；`slog` 结构化输出到 journald；密钥/openid/token 不落日志 |
| 备份 | `mysqldump --single-transaction` 每日 → COS；每季度做一次恢复演练 |

## 13. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 本机 mock 数据与云端数据并存 | 用户困惑"我的数据去哪了" | 双模式只在开发/演示使用；正式构建 `demoMode=false`；首次登录提示数据将从本机迁移或忽略（用 `schemaVersion` 标记，一次性处理） |
| 宠物本地数据将来上云 | 迁移复杂 | 现在就给本地存储加 `schemaVersion`，未来做一次性迁移；不承诺跨设备同步直到真正接入 |
| 微信主体类目 / 备案 | 无法正式发布 | 先用体验版验证产品；推广前集中处理 |
| 单人开发节奏中断 | 半完成状态 | 里程碑按"可运行"切分，每个里程碑结束都能交付使用 |
| 服务端安全 | 数据泄露 | MySQL 不暴露公网（SSH 隧道）；token 只存哈希；密钥走环境变量；不信任客户端身份 |
